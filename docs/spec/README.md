# Specifications

What the original game's data contains and how the game behaves, written by the analysts in our own words (`docs/CLEAN_ROOM.md`). Implementers work from these files only.

## Conventions

- **One topic per file**, e.g. `rom-map.md`, `graphics.md`, `ship-physics.md`.
- **Status of each finding:**
  - **[V]** verified, against the data or the running original;
  - **[C]** read from the program by an analyst, not yet verified;
  - **[H]** hypothesis.
- **Addresses:**
  - `ROM 0x1A2B0` is an offset into the PRG ROM, after the 16-byte header;
  - `bank 3:$9C40` is a CPU address with a given 32 KB bank mapped at `$8000`;
  - `RAM $0042` is internal RAM.
- **Numbers:** hex with `0x` for offsets and sizes, `$` for CPU addresses, decimal otherwise. Fixed-point values give their format (e.g. 8.8 signed) and their meaning in pixels per frame.
- **Behaviour** is written as rules, state machines, formulas and tables. Short pseudocode is fine when an algorithm needs it, written at the level of *what* happens, never as a routine-by-routine translation.
- **Frames and steps:** a *frame* is one video frame (60.0988 Hz). A *logic step* is one step of the game's logic: every second frame in gameplay, every frame elsewhere (`game-flow.md`). Say which one a rate or count refers to. Where the original's timing depends on the hardware (lag, dropped passes, sprite limits, flicker, video-memory bandwidth), say so, so the remake can drop it (`PLAN.md`, "Fidelity"; `docs/deviations.md`).
- **Never:** 6502 assembly, decompiler output, or labels and names from the analysis workspace.
